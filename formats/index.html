A file format won't fix vague BIM

An IFC or COBie file is a printout of the model. It is not a plan, and it goes stale.

Quebec's government BIM roadmap promotes "open BIM": IFC model files, IDS requirement files, the bSDD data dictionary and the other buildingSMART standards. Its guidance document, written by Érik Poirier and Cloé Arnould and approved in May 2025, is a serious piece of work.1 One disclosure up front: OpenBEP's founder works at VIM, a company with its own exchange format, which this page discusses with other alternatives near the end. We agree with parts of it. We disagree with an idea we hear often: that if public owners require IFC and open tools on every project, the industry's BIM problems will go away.

In our experience, the main problem is not the file format. It is that owners ask for "the BIM" without saying what it is for. A vague model saved as IFC is still a vague model.

The argument in short

  • An export is a PDF of the model. You can read it, but nobody can keep working in it. The next team still needs the native files, and the export is out of date at the first renovation.
  • A format says how to write a file, not what goes in it. Only the owner's requirements say that: the uses, the elements, the parameters, the checks.
  • IFC is hard to implement and hard to read. It splits into dialects, struggles with large models, and its next version is a redesign that is not ready.
  • COBie is worse. It is a spreadsheet export that is hard to check and trace back to the model. The UK required it and some clients could not use what they got, and buildingSMART is developing a successor.
  • Some open standards are genuinely good. IDS for requirements and BCF for issues are worth requiring.

This is a disagreement about priorities and order, not about anyone's good faith. The guide itself calls open BIM "naturally desirable" and sets no obligation or date.1 Quotes from French and Dutch sources are our translations.

What open BIM gets right

  • Start with the uses. The guide's own summary says "everything starts with the use cases".1 That is exactly where OpenBEP starts.
  • Owners must control their data. The guide says it is "of capital importance" that public owners keep control of their data.1 We agree.
  • IDS for requirements. An IDS file is a machine-readable list of what each element must carry. The guide says it is "typically the client who develops the IDS".1 IDS is written against IFC classes and property sets, but with a mapping from Revit parameters the same list can be checked against Revit models too, not only IFC files. OpenBEP exports one from every plan for this reason.
  • BCF for issues. BCF, the BIM Collaboration Format, is a good, simple standard for passing clash and coordination issues between tools, with a viewpoint and a comment attached to each one. It does one job and does it well.
  • Checking files. buildingSMART now offers a free online IFC validation service, which the guide describes for owners checking the files they receive.1

Notice what these have in common. IDS and BCF describe requirements and issues. They do not try to be the master copy of the model.

An export is a PDF of the model

The guide says open formats "guarantee interoperability between software" and that data exchange "will be done with interoperable files encoded in the IFC schema".1 A format guarantees that another program can open the file. It does not make the file a working model.

  • Even advocates of IFC use this comparison. In a 2019 interview, an IFC file from a Revit model was likened to a PDF made from a Word file: you can read the text, but you cannot do word processing in it.2 The point then was that anyone can read it. Our point is the other half: in the authoring tools most firms use, you cannot keep working in it.
  • Revit's own help says that opening an IFC file creates a new model from the default template, and points users to linking the IFC as reference information instead.4
  • There is a fair counterpoint: some tools, such as Bonsai (formerly BlenderBIM), author directly in IFC, so for them IFC is the native file. Few Quebec firms work that way today, and a requirement should fit how projects are actually delivered.
  • The Netherlands keeps IFC on the "comply or explain" list that public bodies must require. But in 2019 its Standardisation Forum made clear that IFC models are an output of the source model for communication and coordination, and that "they do not replace the source models".5

Stale at the first renovation.

A delivered IFC or COBie file is a snapshot. In 2016 a senior BIM engineer described COBie as the BIM equivalent of the two-inch thick phone directory that we all used to receive every year – it's out of date even as it lands on your doorstep.6 In our experience the same is true of an IFC archive. The day the building is renovated, the work happens in the native model, which is updated, and the IFC and COBie files have to be exported again. An archive of exports is an archive of old printouts.

So the native authoring files should be the contractual master, and exports are extra outputs, asked for when a named use needs them. This has a cost we accept openly: native files tie the archive to one vendor's format, which is the lock-in the guide warns about.1 Our answer is that an owner keeps control by owning the native files and by stating, use by use, what data it needs and in which format. A blanket IFC rule does not give that control on its own.

Filtering is a feature, if the owner sets the filter.

The guide warns that an IFC export "will necessarily be filtered and will not contain all the data of the original model".1 That is presented as a weakness. We see it the other way. An owner does not want every working parameter and every helper object a designer used. It wants the data its uses need, and nothing else. That is the idea behind our LOD specification, where the as-built level keeps less than the construction model, not more. The problem is not that exports filter. It is that, without owner requirements, nobody decides what the filter keeps.

The problem with IFC

Requiring IFC on every project means asking every firm to carry the weight of the standard as it is today. buildingSMART, the body that maintains IFC, and the researchers who work with it have been frank about that weight.

Too big to implement, so it splits into dialects.

  • buildingSMART's own blog: This rich set of agreements is often too much for a software developer to implement in full into their software tool. Software therefore implements subsets, called model view definitions (MVDs).10
  • The same article counts almost 20 MVDs in the next release: That means 20 different dialects of IFC. Twenty different implementations in software. When this continues the number of MVDs will reach hundred before we realize it. It admits As a community we have been explaining to outsiders that 'there is no one IFC', and calls the approach not sustainable.10
  • A 2021 study inspected 57 IFC models from practice, almost all in the older IFC2x3 version, which is still what much of the market exchanges. IFC's flexibility allows several interpretations, which results in heterogeneous IFC solutions for similar situations which significantly hinders interoperability. Only 8 of the 39 models checked had sufficient semantics.11
  • So "deliver an IFC" in a contract means little on its own. Someone has to say which version, which subset and which properties, and check that the receiving software supports them.

Geometry that does not scale.

  • The technical coordinator of buildingSMART Spain wrote in 2024 that IFC's STEP-based structure led to large file sizes and limited scalability, which affected the adoption and effectiveness of IFC in larger and more complex projects.22
  • Revizto, a coordination software maker that supports IFC, says IFC files can expand to 5-10 times the original file size in some cases, and that the impact is most pronounced in larger projects.23
  • buildingSMART's own blog says the current resource layer (mainly geometry) needs a cleanup.10 Quebec's guide itself warns that IFC files can become large and demanding, so models must be split into smaller files.1
  • The fix explored for IFC 5 is telling: triangular meshes as the main geometric representation, and repeated objects that inherit their geometry from a single typical element instead of being written out again.22 In other words, the way game engines and fast viewers have stored geometry for years.

A standard that keeps changing.

  • The guide counts more than 18 versions of the schema since 1997, and says IFC 5 "will adopt a completely new approach".1 IFC 4.3 became the ISO standard only in 2024.1
  • In October 2026, buildingSMART's IFC 5 repository still calls its examples preliminary and not suitable for production use, says Further documentation will follow soon, and warns that future updates to the development will require revisions to these examples.12
  • buildingSMART Spain's coordinator again: adding new concepts often requires significant changes, which can lead to incompatibilities between versions and difficulties in adopting new features.22
  • So the market stays on the old versions. Under a post about IFC 5, Ivan Shtaer wrote: implementing support for each new scheme every 4-5 years simply does not pay off. The market does not have time to digest this. The developer is forced to support versions 2X3 because a lot of data was created and exists in this format.19 IFC 4.3 is stable and an ISO standard, but a firm that tunes its exports for it today should expect to do much of that work again for IFC 5.

Hard to read.

This one is our own view, from daily work: the IFC documentation is some of the hardest technical documentation in our industry to use, even for experienced BIM managers. Finding how one property of one element should be written means going through layers of entities, property sets, MVDs and versions. buildingSMART itself calls MVD one of the most confusing acronyms in its vocabulary.10 A standard that experts struggle to read is a poor base for a requirement placed on every firm, large or small.

The internet comparison does not hold.

The guide asks readers to imagine the internet without standards like HTML and HTTP, where "you would need a different browser for each website".1 But a web page looks the same in every browser. Two IFC files of the same wall from two tools often do not: different classes, different property names, missing data, as the 2021 study found.11 The guide also promises data that "can be used in asset management software decades later".1 Data kept for decades is only useful if it was consistent in the first place: the same parameters, with the same names, filled in the same way on every project. IFC does not give you that. A shared parameter list and owner requirements do.

The problem with COBie

COBie is a spreadsheet handover format, built as a subset of IFC. The UK government's 2011 construction strategy required it on centrally funded projects.37 That was a format requirement at national scale, and the results are on record.

  • Clients who asked for the format, not the content. Birmingham City University's BIM process manager: When a client just says ‘give me COBie’ without identifying their specific requirements, consultants will be ripping their hair out because that level of information is just not needed to manage buildings. It’s a big job for someone that will have to be paid for unnecessarily.3
  • Data that could not reach the client's systems. In 2016, the year the UK mandate took effect, three of the people BIM+ interviewed reported difficulty importing COBie data into their maintenance software. Hampshire County Council's framework manager: We want to be able to transfer data into our CAFM systems after project delivery, but have not delivered that yet. In the same survey, 58% of respondents said they had never used BS 1192-4, the standard that describes COBie.3
  • A short list was enough. When Argent, the developer of London's King's Cross, asked its asset managers, facilities managers and tenants what they actually needed, the answer was quite a short list. Its BIM lead: Full COBie data drops are not the route we want to go down.3
  • Still misunderstood years later. In 2020, John Ford, a contractor's digital lead and an advocate of IFC and COBie, wrote that the lack of understanding of what COBie is, its purpose and how it is driven by IFC were three of its fundamental barriers today, followed by the lack of native support in software.7
  • Contracts that pay for files, not information. In a 2020 UK government-funded consultation, every respondent on contracts agreed that common contracts drive the delivery of documents, not the delivery of usable, accessible, sufficient quality information.8
  • Generic requirements. In Wales, a 2026 study heard: We get EIRs that are either copied from old projects or so generic they're useless. Participants described COBie outputs delivered as static spreadsheets late in delivery.9

To be fair, the 2016 article also quotes clients who valued full COBie data, such as Sandwell council for its housing.3 The difference is that those clients knew what they would do with the data.

Why it fails, in our view.

The points below are our own view, from daily work on Revit projects.

  • It is not much more than a schedule export. A COBie workbook is a set of linked spreadsheet tabs. Apart from its links between spaces, zones, systems, spares and contacts, most of what it holds is what a Revit schedule exported to Excel or CSV would hold, with more ceremony.
  • It cannot easily take you back to the model. The identifier in a COBie row is usually the IFC GlobalId, not the Revit element ID. Revit's Select by ID does not accept it; you need a plug-in, or a parameter the exporter stored, to find the element.
  • You cannot tell where a value came from. COBie defines the columns, but not which model parameter feeds each one. The same value can come from several parameters, be renamed or be merged on the way out, and the file does not record which. Two teams rarely fill it in the same way.
  • It needs consultants. Getting a team to deliver valid COBie takes training, checking tools and outside help, and a business of courses and services has grown around it. Bilal Succar, on the churn of handover standards from COBie to its successor: Countless people spent countless hours learning, implementing, resolving, and accommodating. Some have built learning materials and business offerings around A and B. They will have to do it again now, soon, and then again in the future. His letters stand for each successive standard.17

The tools around it.

The checking software tells the same story. In 2016 the US Engineer Research and Development Center released an open-source COBie checker, COBieQCReporter. Bill East, who created COBie, wrote that it depended on Java code Oracle stopped updating in 2019, and that efforts to revive it or crowd-fund a replacement since 2019 were without success.25 His current checker, COBieQC, is not sold. Per his site, a user gets a complimentary 12-month copy after buying a printed user's manual, one per user, through a print-on-demand service. Trial versions are not available. The licence is checked online Every time the software starts, and technical support is not provided.24 Bill East describes the software as a volunteer effort,25 and we do not doubt the work behind it. Other checkers exist in commercial tools. But an owner requiring COBie should know that the reference checker from its creator comes on these terms.

  • buildingSMART is developing a new framework, Asset Operations Handover, described as COBie's successor. Justin Kirby, writing up a Digital Construction Week talk by Skanska's head of digital construction, says COBie's rigid, spreadsheet-centric approach has increasingly led to massive data waste. It's highly effective at being written into contracts, but historically terrible at actually being used by the teams running, cleaning, and maintaining the buildings.16
  • Bill East replied: The focus of COBie as a "spreadsheet' has always missed the point. It is about process - where consultants and subcontractors are required to deliver information when first created. Without process change you can call it whatever you want and it still won't work.16 On this we agree with him: the process is the point, and a format requirement does not deliver a process.

An owner who asks for COBie today is paying for a format on its way out. Ask operations for the short list of data they use, in the format their system imports.

ISO 19650 is not a revelation

ISO 19650 is often presented as if being an international standard made it the one source of truth. It is useful, but most of its core ideas were published years earlier, for free.

  • In 2010, Penn State's Computer Integrated Construction research group published its BIM Project Execution Planning Guide under a Creative Commons licence. Its procedure has four primary steps: 1) identify BIM Goals and BIM Uses, 2) design BIM Project Execution Process, 3) develop Information Exchanges, 4) define supporting infrastructure for BIM Implementation.13
  • ISO 19650-1 and -2 came out in 2018. They replaced British standards which, in the UK guidance's own words, formed the basis of the UK approach to BIM.14 The UK guidance also says plainly: The information content is the same information which has always been required during an asset's lifecycle.15
  • In our reading, set side by side, much of it is a renaming. Penn State's BIM goals and uses became the owner's "information requirements". Its information exchanges became "exchange information requirements" and delivery plans. Its BIM Project Execution Plan became the "BIM execution plan". ISO 19650 does add useful things from the British standards, such as the chain of appointments and the workflow of the common data environment.
  • So ISO 19650 is a good shared vocabulary for contracts. It does not tell an owner which uses it needs, and its text is sold under licence while Penn State's guide is free.

Free tools are not the bottleneck

Open-source tools are welcome, and several can already write IDS files.1 But in our experience, the price of a licence is rarely what stops a project from getting useful BIM. What stops it is an owner who cannot say what it needs, a team that was never trained to deliver it, and nobody checking the result. What the Welsh study's participants asked for was practical templates, worked examples and validation tools.9 A free tool in untrained hands produces a free vague model.

Other designs worth watching

If the industry wants open exchange that copes with very large models, it is worth looking at formats designed for that from the start. None of them is an ISO standard, and each is backed by one company or a small community. All of them are newer than IFC, and the claims below come from their own documentation; we have not benchmarked them.

Fragments, by That Open Company

That Open Company, the team behind IFC.js, publishes Fragments, which it describes as an open BIM format optimized for handling large datasets efficiently: binary, compact, and supporting geometries, properties, and relationships. Its viewer is designed to handle millions of elements in seconds. The format is built on Google's FlatBuffers, so anyone can write a reader or writer in any language, and the libraries are published under the MIT licence.28 Its README says the easiest way to make Fragments is its built-in IFC importer, so today it builds on IFC rather than replacing it.28

VIM

Disclosure: OpenBEP's founder works at VIM, the company behind this format. Weigh this part with that in mind.

An open-licence (MIT) binary format from the author's employer. Its specification describes it as a modern and efficient open 3D data interchange format designed for BIM and manufacturing data optimized for efficient loading and rendering on low-power devices.26 Geometry is instanced triangle meshes; BIM data is relational tables.26

  • A value can be traced back. Unlike a COBie row, each element row keeps the Revit element id and unique id and the source file it came from, and every parameter value points to a descriptor with the parameter's name, group, instance-or-type flag and shared-parameter GUID.33 A checker can say which parameter, on which element, in which file, gave a value.
  • The model's own structure is kept. Worksets, phases, levels, design options, views and the volume and area of each material in each element are stored as tables, with the Revit category as authored; nothing is downgraded to a generic class.33
  • Open code. The format libraries and a React-based web viewer are published under the MIT licence.27
  • Limits. It is one company's format, not an ISO standard. It stores meshes only, no parametric geometry. It is an export, so it goes stale like any export. Grids and level datums are exported poorly today, and its own specification documents cases where Revit ids repeat across linked files.33 We have not benchmarked it against IFC and make no claim about size or speed.

And others

  • Speckle is an open-source data hub that connects with your favorite AEC tools and streams objects between them, with an Apache-2.0 web viewer.29
  • dotbim is an open-source and minimalist file format for BIM, MIT-licensed, with triangulated meshes only and one page of documentation, against 100+ for IFC by its own count.30
  • iTwin.js, from Bentley, is An open source library for creating, querying, modifying, and displaying Infrastructure Digital Twins, under the MIT licence.31
  • OpenUSD, the scene format created by Pixar, is, in its industry alliance's words, now being embraced by industries beyond the film industry, including architecture, engineering, construction.32 The IFC 5 work borrows ideas from it.22

We are not asking owners to require any of these instead of IFC. Like IFC, they are exports, not authoring masters, so the native files still matter. Our point is narrower: a requirement written only as "deliver IFC" fixes the container, while a requirement written as "deliver this data, checkable against this IDS" fixes what matters and leaves room for better containers.

What practitioners say

We read public LinkedIn posts and the replies under them, including under buildingSMART International's own posts. Quotes are word for word. Where someone's role was not shown, we give only their name. The people defending IFC are quoted too.

  • Marko Lazic: Two decades of standards, and "just send me the IFC" is still the sentence that ruins an afternoon. And: Every real project has a folder of half-broken exports and one person whose whole job is fixing what the format dropped.18
  • Jelena Stevanovic, replying: IFC is often treated as the solution, when in reality it is only the container. Without clearly defined information requirements and proper QA, "open BIM" remains more promise than process.18
  • Mayur Tanna, in the same thread, audited one federated IFC of about 3,200 objects: 352 elements exported as IfcBuildingElementProxy — their real class lost at export. 793 federation duplicates, and 133 storeys that are really 28 levels. He adds: How much is the format and how much is export settings, I can't tell from the receiving end.18
  • Stefan Kovacs, replying to buildingSMART International's post about its 2026 Tokyo summit: The development of applications is progressing well, but mainly on a very theoretical level. As paying operators and builders, we need fast solutions (problem solving user cases)that support us in our tasks. He asks buildingSMART to set targets with time lines for the industry.20
  • Birgitta Schock, of buildingSMART Switzerland: openBIM has reached a level of technical maturity that would have seemed ambitious a decade ago. Yet many organisations still struggle to formulate what they actually want to achieve with it.21

The other side

  • Steven S., replying to Lazic: "Just send me the IFC" is not an information requirement. In his view the sender and receiver often never defined the actual exchange properly, so the fault is not always IFC's.18 Erik Björnhage made the same point: Working with IFC is not really a problem, as long as everyone understands what they are asking for and what they are getting.18
  • Menno Mekes: major contractors in the Netherlands demand and use IFC as project deliverable even when working with a big platform that only supports native models. And: It just works.19

The defenders and the critics end up in the same place: an exchange works when it has been defined and checked. That definition is the part owners skip, and it is what a BEP is for.

What did it cost?

We looked for measured figures: hours or dollars lost to COBie or IFC deliverables on a named project. We found none published, including in the LinkedIn threads above, where the nearest thing is one practitioner's count of errors in a single IFC file. The sources describe the waste in words, not numbers. If you know of a measured case, tell us and we will add it with its source.

What owners should ask for first

  1. The uses. Name the BIM uses you need, phase by phase: coordination, quantities, permits, operations. No use, no requirement.
  2. The content. For each use, list the elements, the level of development at each stage, and the parameters each element must carry, with the same names on every project.
  3. The master files. Make the native authoring files the contractual deliverable, so the next team, and the next renovation, can keep working.
  4. Checkable requirements. Issue the requirements as an IDS file as well, so a delivery can be checked automatically.
  5. Issues in BCF. Ask for coordination issues in BCF so they move between tools with their viewpoints.
  6. Exports only where a use needs them. Ask for IFC, or another exchange format, when a named party must use the model without the authoring software. Say which version and which properties.
  7. Checks with consequences. Check the model at each milestone and hold payment until it passes.
  8. Handover data people will use. Ask operations for the short list of asset data they actually use, in the format their system imports. Don't ask for COBie by default.

OpenBEP does these steps in order. The owner picks the uses, and the BEP Builder turns them into the plan, the element-by-element requirements, the shared parameters, an IDS file and the milestone checks.

What this page does not say

  • It does not say exports are useless. An export is the right tool when someone without the authoring software must use the model.
  • It does not say open standards are a bad idea. IDS and BCF are worth requiring, and ISO 19650 is a useful vocabulary.
  • It does not question anyone's motives. Much of the evidence on this page comes from buildingSMART and from open BIM's own advocates.
